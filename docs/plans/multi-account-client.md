# Multi-account browser client plan

Status: planning only. Reviewed against `release/server-beta4` at `c681f972330989e0e0d94c2104399fc21f0192c1`. No implementation, production access, or deployment is part of this document.

## Product boundary

The first release supports administrator-created accounts and invitations for a self-host server, used through its browser UI or installed PWA. Preserve the existing owner as the original administrator. Each reader owns a private library, reading state, settings, and source logins. There is no public signup or shared-library UI. Administrator status permits account/server administration; it does not make another reader's library an ordinary selectable library.

The initial client supports **one active cookie account per server origin and browser profile**. Signing out or changing account affects other tabs and the installed PWA when they share that browser cookie store. Different browsers/profiles can use different accounts. Do not add a simultaneous-account tab selector or remember a list of accounts/passwords.

The self-host entrypoint is `src/main.tsx` with `public/sw.js`. `apps/web/src/main.tsx` and `apps/web/src/web-runtime.ts` compose the separate local-static product; its offline database, Google/Cloud Vault login, and service worker are not a second self-host login implementation. Keep that product working without introducing self-host account ownership into its existing local library. Desktop account support is deferred. Changes to shared classes must preserve existing local/native callers.

V1 targets a family/friends server. Account creation does not eagerly start a runtime/container per reader. Unsafe optional collector integrations and whole-server backup/restore remain unavailable to members; ordinary account-library operations follow the backend capability contract. Share runtime capacity only where the backend has an explicit account boundary.

## Identity and request contract

Align exact names with the authentication/backend plan. Proposed client-visible authenticated context:

```ts
interface SelfHostAuthenticatedContext {
  serverId: string;
  account: {
    userId: string;
    username: string;
    displayName: string;
    role: 'admin' | 'member';
  };
  libraryId: string;
  accountId: string;
  sessionContext: string;
  capabilities: readonly string[];
  expiresAt?: string;
}
```

`serverId`, `userId`, and `libraryId` are server-generated stable IDs. `sessionContext` is a random session binding returned by authenticated status/login; it is not a bearer credential and grants nothing without the cookie. Keep it in memory. Existing plugin deployment/account mappings already have persistent IDs: preserve them and expose the mapped plugin account identity as top-level `accountId` in `SelfHostAuthenticatedContext`. Compare plugin `accountId` to that mapped ID, not directly to the account-table `account.userId`. Auth identity resolution must work even when the plugin feature is disabled. Invitation/reset redemption does not create a session or return an authenticated context; the reader signs in afterward.

Use two separate ownership concepts:

- Persistent account scope: an unambiguous encoded tuple of server origin/API deployment, `serverId`, `userId`, and the relevant `libraryId`. Including `serverId` prevents a replacement server at the same URL inheriting another installation's cache. Do not concatenate unchecked strings with ambiguous separators.
- Runtime owner: the persistent scope plus an in-memory session epoch/lifetime. This changes on every authentication replacement, including the same user's re-login. It is captured by asynchronous work and never looked up through a mutable global current-account variable.

Every protected browser JSON/blob/upload/stream request goes through a context-bound transport with `X-BOAA-Session-Context`. The server validates it against the cookie-resolved session before reading or mutating account state. This is necessary because the browser can replace its cookie before another tab receives an account-change event. Client cancellation and BroadcastChannel alone cannot stop a stale A tab from sending work with B's cookie.

`409 session_context_mismatch` means end the old runtime and re-check authentication; do not retry the operation under the new session. `401` ends the current session. Gate events must include the originating runtime epoch, so a late A error cannot sign out newly authenticated B. `403` for an admin-only capability leaves a valid member session signed in; source-login-required/source-access-denied errors remain source-specific. Transport/network failures do not infer logout or permission denial.

The status endpoint discovers the current context and is not bound to an old context. Logout must be context-bound: a stale A tab must not revoke or clear B's cookie. Only `/login` supports deliberate session replacement through `replaceCurrentSession` plus the matching expected session context; otherwise an existing-session conflict is returned. Invitation/reset redemption rejects an active authenticated cookie with `409 account_session_active`: explicitly log out, redeem the token, then return to login. Context mismatch must not send a cookie-clearing/replacement response. First setup is anonymous and one-time; no authenticated background task may perform these transition operations. Role/capability checks in the UI are discoverability controls; the server remains authoritative.

Audit direct `fetch` paths as well as `RemoteApiClient`: plugin HTTP/context, managed metadata/source brokers, downloads, import progress, and provider clients. Plain `img`, `audio`, `video`, iframe, and navigation requests cannot add the context header. Use a context-checked fetch followed by an owned blob URL, or a narrow server-issued session-bound media/download grant. Existing tickets must be audited for session/account ownership and expiry; a book ID or cache hash alone is insufficient. Old grants must not authorize another account and must obey session-revocation policy. Do not put the session cookie, expected-context value, or bearer credentials in query strings.

Prefer invitation/reset token transport in the URL fragment, then exchange via POST. ## One transition owner for the application

Introduce an authenticated runtime boundary above `RuntimeProvider`, the plugin provider, and `App`. Its state machine is `checking -> signedOut/setup/invite -> authenticating -> hydrating -> ready`, with `ready -> quiescing -> signedOut/checking` for logout, expiry, context mismatch, and cross-tab changes. Connection errors are explicit states. This boundary owns the session lifetime, active identity, cancellation registry, and pending transition generation.

The transition sequence is mandatory; implementation details can reuse existing controllers:

1. **Fence the old session synchronously.** Block new commands, remove private content and metadata from the rendered shell, stop media/TTS and clear Media Session metadata, invalidate the transition generation, and broadcast invalidation. Capture final progress into an old-account-owned checkpoint while its owner is still known.
2. **Finish only safe old-session persistence.** For deliberate logout, permit a bounded final flush through the old context before its request lifetime is revoked. Failure must not block sign-out indefinitely. On expiry/context mismatch/account replacement, do not send a cleanup flush with ambient cookies: retain any retryable checkpoint only under the original account, or report uncommitted progress. React unmount/pagehide cleanup must not bypass this rule.
3. **Dispose local work.** Abort all requests/body reads, import upload/poll loops, discovery/catalog requests, covers, source-stream prefetch, browser downloads, OAuth/popup continuations, AI/TTS polling, and scheduled autosaves. Invalidate queued reader-position persistence and shared paragraph pages. Close source/read handles, file/OCR/parser workers, plugin workers/sessions, listeners, timers, and account-owned storage handles. Clear owned caches and revoke every created object URL. Closed/disposed objects must reject later work rather than silently restart.
4. **Revoke or replace server authentication.** An explicit sign-out uses the old expected context; server session invalidation uses its defined auth flow. Keep teardown usable if revocation fails. Discard all late responses, including late 401s, toasts, cache writes, and job-completion callbacks from the old epoch. The control-plane auth client is separate from the already-aborted data client.
5. **Verify and construct the new owner.** Resolve current authenticated context and create fresh repositories, clients, providers, extension registries, source brokers, stores, and caches from that immutable context. Never switch a live repository's account property in place.
6. **Hydrate before enabling commands.** Load that account's settings/source configuration, verify plugin context, and open account storage. Recovery queues and progress journals select only the current owner. Render the private app once required hydration succeeds; optional feature failures may have their own retry states. A failed source/settings hydration must not be interpreted as empty history and trigger destructive sync or migration.

The bounded final-flush phase must not be a long period in which private UI remains visible. On teardown failure, fail closed; a reload is a recovery path after stale resources are fenced, not a substitute for namespaced storage or server checks. Existing `SessionCoverCache.clear()`, source stream close/abort, `invalidateSharedParagraphPages`, `invalidateReaderPositionPersistence`, `useLibrarySourceFilesController` ownership checks, TTS ownership checks, and `ProductPluginSession.close()` are building blocks. Add disposal where ownership is currently implicit.

**Logout cancels browser activity, not previously accepted server jobs.** Committed import/download/AI/TTS jobs continue for their owning account under backend policy and can be rediscovered after that account signs in again. Do not call server job cancel merely because a panel or session unmounts. Stop polling and local transfers; cancel a server job only through its explicit user action or an agreed ephemeral-session cleanup contract. Closing an interactive source-login browser can release its temporary lease without deleting the account's saved source login.

## Storage and credential ownership

Provide explicit scoped storage/database ports to self-host components. An account-specific database name or complete compound-key/index scheme is acceptable, but every read, enumeration, index, delete, retention, recovery, and quota calculation must use the scope. A single mutable global database owner is unsafe. Avoid mixing self-host account records into the existing unscoped local-static library.

At sign-out, always discard decrypted credentials, session key handles, temporary content, runtime caches, OAuth continuations, and blob URLs. Persistent per-account data must never be readable through the signed-out app or another account's adapters. Persisted downloads/checkpoints may remain under their owner when needed for resume; any “remove this account's data from this device” action deletes only that account's records. Do not clear all origin storage and accidentally erase a separate local library or another user's downloads. Namespace isolation is an application boundary, not a claim of protection against someone with access to the browser profile/devtools; self-host authentication must not unlock an offline private library from a mere stored username.

Legacy migration is a release gate:

- Do not assign unscoped browser state to the first person who happens to log in after upgrade.
- Server migration identifies the original owner. Only that authenticated owner can claim matching legacy self-host state, using a versioned one-time marker and explicit server/deployment match.
- Newly invited accounts start empty even when another account previously used the browser. Never fall back from a missing account key to an unscoped/old-brand key in normal operation.
- Keep uncertain local data isolated until ownership can be established; do not silently upload it or delete a local-static library. Migrate/discard reconstructible cache separately from valuable progress, credentials, and explicit downloads.
- Brand-storage aliases and `prepareBrandDatabase` migrations must obey the same owner boundary and must not resurrect unscoped values into every account namespace.

## Tabs, restoration, and service workers

Add an application auth channel scoped to server origin/deployment, with `BroadcastChannel` and a non-secret `storage`-event fallback. Messages announce only invalidation/change and a monotonically handled generation or unique event ID; they carry no passwords, invitations, source data, or bearer/session secrets. A receiving tab locks immediately and asks the server for current identity. Never accept a broadcast message as proof of which account is authenticated.

Revalidate on startup, focus/visibility restoration, and `pageshow` after bfcache restoration. Register a locked/neutral restoration boundary so back/forward navigation cannot display old private DOM while a check is pending. Stop stale hidden-tab timers and prohibit writes until revalidation. Use the expected-context request check for correctness when channels are missing, suspended, delayed, or messages race. Test a suspended PWA and a live browser tab as well as two ordinary tabs. The existing plugin auth channel should participate in the application transition rather than leave two independent definitions of login state.

Keep the self-host service worker limited to a public application shell and static assets. `/api/` bypass is necessary but does not address the browser HTTP cache: server auth/private data/media responses need suitable `Cache-Control`/`Vary` behavior, and identity-sensitive client requests should not retrieve stale responses. The shell must contain no account data. A deploy changes cache version and retires any previous sensitive navigation entries; navigation caching must use a sanitized public shell key. No logout should unregister the entire app shell or delete the separate local-static product's offline data.

Offline startup shows that a server connection is needed to verify the account. It does not reveal cached library titles, source results, reading history, thumbnails, private audio, or the previous account's name from an unverified cache. This release adds no offline identity unlock mechanism.

## Essential acceptance tests

Use synthetic accounts A/B and synthetic connectors/content only. Create the same book, chapter, source, cache, and workflow IDs in both accounts to make accidental ID-based sharing observable. Most tests belong at the state/transport/storage boundary; add a small real-browser two-tab/PWA suite for cookie, storage, bfcache, and worker behavior.

1. **Setup and invitation:** first setup remains one-time; member sees no signup/admin screen; only admin can create/revoke/reset invitations; expired/used/revoked tokens cannot be redeemed; two redemption attempts have one winner. Successful invitation/reset redemption creates no session and returns the UI to login. An active cookie produces `409 account_session_active` without consuming the token or replacing the session; explicit logout then redemption succeeds. Only `/login` accepts `replaceCurrentSession` with the matching expected context. Invitation/reset tokens are absent from history after extraction, persistent browser storage, cache keys, diagnostics, and unrelated requests.
2. **Account identity:** changing A's display name preserves its cache/settings. Use synthetic identity fixtures to prove storage follows immutable IDs even if a username changes or another ID receives the same username; these are invariants, not offered V1 rename/delete/recreate features. Replace a server at the same URL and verify old storage is not adopted. Plugin context must match top-level auth `accountId`, not `account.userId`, and inconsistent mappings cannot start.
3. **Runtime teardown:** defer paragraph/cover/catalog/source-login/AI/import/settings responses and complete them after A logs out/B logs in. No A content, toast, navigation, DOM, persistence, or new object URL appears in B. A late 401/context mismatch does not end B's valid runtime. Verify disposal also under React StrictMode and repeated transitions.
4. **Cookie race:** keep A's tab busy, sign in as B in another tab, delay/drop broadcast delivery, then run A's queued read/write/upload/progress flush. The server rejects A's expected context; B's library is unchanged and A sees no B response. A late logout must not clear B's cookie. No blind retry changes the operation owner.
5. **Storage isolation:** exercise list/read/save/delete/recovery/retention on source credentials and catalogs, device settings, discovery, source offsets/visits, fixed-document text, enrichment, hosted audio/download jobs, extension enablement, Cloud Vault/file handles, and workflow IDs. A cannot see/delete/replay B's state. A new invitation receives no auto-imported legacy integration settings. Legacy-owner migration is repeatable without duplication and never runs for B.
6. **Reader final position:** deliberate logout checkpoints/flushes the last text, image, fixed-document, and listening position to A with a bounded wait. Expiry or account replacement never sends that checkpoint as B. Re-login as A recovers only A's valid revision; an interrupted pagehide/unmount flush cannot escape the owner fence.
7. **Media/source sessions:** sign out during image/text streaming, cover loading, audio playback, file export, and OAuth/source-login completion. Playback and source prefetch stop, handles close, old blob URLs are revoked, and late callbacks do not reconnect B. Direct media/download grants reject reuse under the wrong account/session according to their contract.
8. **Jobs and failures:** logout stops client polling/transfers but does not cancel an accepted A server job; A can rediscover it, B cannot see its ID/status/results. Failed logout locks locally, survives reload without auto-restoring A, accurately reports pending server revocation, and safely completes after reconnect. An aborted browser upload has a defined backend cleanup path without cancelling unrelated jobs.
9. **Tabs and PWA:** logout, session expiry, account disable, password reset, and A-to-B login invalidate all relevant clients. Cover active, backgrounded, bfcache-restored, offline, and no-BroadcastChannel cases. Restored pages do not flash private DOM, document titles, playback metadata, or cached source results.
10. **HTTP/error behavior:** protected transport includes context and lifetime cancellation; blob/progress/direct-fetch paths receive the same checks. 401/context mismatch ends only its owner; 403 admin denial and source-login errors do not cause global logout. Network errors do not auto-import local data or present a false empty server library.
11. **Cache and regression:** authenticated API/media and invitation/reset responses cannot be recovered from service-worker caches after logout. Public shell assets still work. Existing local-static browser tests remain valid; shared reader/source lifecycle tests still pass; desktop builds are not silently advertised as supporting multiple accounts.
12. **Administration versus personal settings:** members cannot invoke executable-extension/runtime install/update/remove, global network defaults, unsafe collectors, or server backup/restore by calling hidden endpoints directly. Provisioning an approved source creates an empty account binding with no administrator preference, history, or credential. Member enablement and login changes affect only that member. Creating an idle member does not start an idle dedicated runtime/container.

Relevant existing suites to extend include `SelfHostAccountGate.test.tsx`, `self-host-auth-client.test.ts`, `src/test/remote-api-client.test.ts`, external-source local-state/cover/journal tests, `shared-paragraph-pages.test.tsx`, reader progress/lifecycle tests, hosted TTS cache/download tests, plugin session/provider tests, source-file ownership tests, and the self-host browser smoke harness. `apps/web/src/service-worker.test.ts` validates the separate worker; add checks for the self-host `public/sw.js` itself rather than assuming those tests cover it.

## Implementation order and release gates

1. Finalize identity, expected-context checks, capability/error codes, invitation/reset flows, and session-bound media contracts with the auth/backend work. Keep new-account creation gated until isolation is complete.
2. Add the authenticated runtime owner and lifetime-bound transport; migrate direct authenticated fetches and plugin identity validation. Introduce teardown tests before wiring additional screens.
3. Scope all remote browser persistence and credentials, including indirect default-store constructors. Implement original-owner-only legacy migration and block unsafe fallback reads.
4. Wire login/invitation/account administration and account-aware settings into the existing UI; add cross-tab/PWA/bfcache handling and neutral hydration/error states.
5. Run focused client tests and the synthetic two-account browser isolation suite together with backend isolation tests. Release only when stale-tab request rejection, identical-ID storage isolation, legacy migration, private media, and full teardown pass. A login form plus database ownership is not a sufficient release boundary.

## Implementation evidence: importer-confirmed source IDs (2026-10-18)

Hosted member imports may replace the provisional `clientBookId` with an owner-scoped canonical book ID. Source links now adopt the import result's `novel.id`; document-series batches carry that ID into subsequent snapshots, assembly, append and retry. Existing revision-bound links cannot be redirected to another book. Remote source/work/section identifiers remain unchanged: saved stream lookup and reading positions continue to resolve the actual library book through the finalized link.

Before final link activation, the confirmed ID is checkpointed in the pending intent under its operation-ID compare-and-swap. If finalization is interrupted, catalog reconciliation uses that confirmed receipt rather than matching books by equal content bytes. A hosted first import whose result never reached the client remains an unresolved pending intent; the client does not know whether the server committed it and cannot automatically locate the final book under the current API. Such intents are retained rather than treated as proof that library content was deleted. No remote result-lookup API or hash-based ownership inference was added. The actual server library remains authoritative; automatic pre-result crash recovery is a known limitation, requiring an explicit follow-up recovery workflow rather than blind reimport or deletion.
