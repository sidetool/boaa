# Multi-account identity and administration plan

Read-only architecture review at `c681f97`, 2026-10-18. This document proposes implementation; it does not claim production inspection or completed isolation. Coordinate delivery with the data-isolation and browser/runtime plans.

## Confirmed scope

- Self-hosted web/PWA accounts for family/friends, created and invited by the administrator; no public signup, email service, OAuth provider, organization framework, or local-profile model.
- Preserve the existing installation's account as administrator, with exactly the same `user_id`, library, reader state, credentials, sessions, and plugin identity.
- Members receive separate libraries, reading history, source credentials, and settings. Administrator status authorizes account/server administration; it does not make another user's content accessible through ordinary library APIs.
- First delivery supports one protected existing/bootstrap administrator and member accounts. Role promotion, administrator transfer, impersonation, destructive account deletion, and cross-account library sharing are outside scope. Disable/re-enable preserves data. Desktop-managed runtime remains outside the new account UI; its existing owner bearer access remains compatible.
- Deliver account creation only after route/resource/runtime/browser isolation is complete. Merely removing the singleton constraint is unsafe.

## Authoritative identity contract

Add shared wire contracts in the existing `packages/contracts` layout rather than separately maintained frontend/backend interfaces:

```ts
type SelfHostAccount = {
  userId: string; // immutable database owner ID
  username: string;
  displayName: string;
  role: 'admin' | 'member';
};
type SelfHostAuthenticatedContext = {
  account: SelfHostAccount;
  serverId: string; // existing deployment identity
  libraryId: string; // existing deployment/library identity
  accountId: string; // existing plugin account incarnation identity
  sessionContext: string; // independent random value; not a login credential
};
type RequestPrincipal = {
  userId: string;
  role: 'admin' | 'member';
  authMethod: 'session' | 'legacy-token';
  sessionContext?: string;
  authVersion?: number;
};
```

Decorate `FastifyRequest` with a per-request nullable principal. Provide `requirePrincipal`, `requireUserId`, and `requireAdmin` helpers that fail closed. Never accept ownership from request JSON/query/headers, a client role, or a fallback to `defaultUserId`. Shared configuration remains immutable; do not mutate `config.defaultUserId` during requests. Background tasks retain the creating owner's identity from authoritative persisted task/upload rows.

`authenticateSession` should return an internal session principal, not a password-bearing account row. Keep password fields confined to the login/password service. Account status/role and session authorization version are checked on every request; avoid a long-lived authorization cache that survives disable/revoke.

Refactor the existing deployment/account identity resolver so auth status/session can expose the same IDs even when `JS_PLUGIN_ORIGIN` is unset. Preserve all existing `plugin_deployment_identity` and `plugin_account_identity` values. New users get their own account incarnation. Plugin approval still requires a cookie session; a deployment bearer token must not gain plugin-approval authority.

For cookie-authenticated JSON/blob/fetch/stream APIs, send and require `X-BOAA-Session-Context`, matched to the cookie-resolved session. A stale A tab must not read or write using B's newly shared cookie. Return `409 {error:'session_context_mismatch'}` before work; do not replay the request, revoke B, or clear/set B's cookie. Use an independent per-session random context so an old A session cannot silently become a new A session. Update CORS's allowed-header contract.

Auth status/session are context-discovery exceptions. Login/setup can run without context when anonymous; replacing an authenticated session requires `replaceCurrentSession: true` plus the expected current context. Invitation/reset redemption does not auto-login and rejects an active cookie session with `409 account_session_active`; its screen lets the user explicitly log out with the expected context before proceeding. Logout/password-change/logout-all and administrator session revocation require expected context. Public auth-hook exemptions do not exempt these handlers from their own context/origin checks. Direct image/media/download navigation cannot set headers: migrate those consumers to fetch-to-blob or narrow, session-bound asset grants; grant validation must recheck issuing-session validity. Do not enforce the header indiscriminately before these consumers are handled.

## Migration and account storage

Append the next migration after 0058 and update the consolidated snapshot. Run it through the existing checksum/advisory-lock migration runner; never rewrite previously applied migrations.

1. Preserve the current account row and every related user/resource row. Replace singleton primary-key semantics with `user_id` primary key, preserving the existing unique constraint/index required by `plugin_account_identity` until its FK dependencies are safely handled. Do not drop a referenced unique constraint casually.
2. Retain a database-enforced bootstrap-owner marker, for example convert/rename the current `singleton_key` into a nullable unique `bootstrap_owner_key` that only accepts 1. Existing row retains 1; member rows get null. This preserves a stable original-owner association and an atomic winner for concurrent first setup. Runtime singleton account lookup is removed.
3. Add `role` constrained to admin/member with member default; explicitly backfill only the pre-existing/bootstrap owner as admin. Add `status` constrained to invited/active/disabled, with the existing row active. Protect the bootstrap administrator from disable/delete/role mutation in this release.
4. Invited accounts need no administrator-known password. Allow password scheme/salt/digest to be jointly null only before activation; constrain all-or-none credential fields and require credentials for active accounts. Disabled invited accounts can return to invited; disabled activated accounts can return to active.
5. Make `users.email` nullable while retaining uniqueness for populated values; keep existing email unchanged. Invite creation transaction inserts a cryptographically random immutable user ID and member account with chosen normalized username. Keep username normalization/unique conflicts consistent with current login. Do not make usernames mutable in this release; display name can be changed transactionally in both existing locations.
6. Add account `auth_version` and session `auth_version`, initially 1 for preserved rows. Add independent random session-context ID, unique per session, backfilled for existing sessions using a migration-supported cryptographic UUID generator (PostgreSQL 16 is the declared deployment). Existing raw session cookies continue to resolve.
7. Add `self_host_account_tokens`: hashed token primary key, account user ID, purpose invite/password-reset, creator user ID, created/expiry/consumed/revoked timestamps. Issuance and consumption are transactional. Expired/consumed/revoked tokens never work; reissuing revokes earlier tokens of the same purpose. Raw tokens are returned only once to the authenticated administrator.
8. Verify existing bootstrap-owner ID equals configured `DEFAULT_USER_ID` before serving legacy bearer or seeding a different default owner. A changed config must fail clearly rather than minting an extra owner or handing the token another library. A fresh/token-only installation still completes first setup against its existing seeded user.

Account creation, bootstrap, activation, disable/enable, reset, password change, and account-wide revoke lock the target account/user row consistently. Hash outside the transaction, then recheck current account status and expected credential/auth version before committing. Session issuance after a concurrently disabled/reset account must fail; a password computation started before reset cannot create a valid post-reset session. Bump `auth_version` and revoke stored sessions together for reset, password change, disable, and explicit revoke-all. Re-enable never revives old sessions.

No user-library export/restore may serialize or overwrite users, accounts, password digests, sessions, invitations, or deployment/account identity. Full operator database backup remains distinct. Existing library objects/IDs and owner-specific credential directories do not move during identity migration.

## API and user flows

All auth/admin responses use `Cache-Control: no-store`; errors contain stable codes without secret material. Require administrator authorization on the server, not only hidden controls. Use existing small auth body limits and JSON parsing.

| Endpoint                                          | Access and behavior                                                                                                                                                                                                                                 |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/auth/status`                            | Public setup state; valid cookie adds authenticated context and role. Never lists accounts or reveals invite records. Retain compatible setup-code fields.                                                                                          |
| `GET /api/auth/session`                           | Resolves valid cookie and returns authenticated context; otherwise 401. Context bootstrap for a refreshed application.                                                                                                                              |
| `POST /api/auth/register`                         | Initial bootstrap owner only, existing setup-code protection and database winner. A completed installation always rejects it.                                                                                                                       |
| `POST /api/auth/login`                            | Normalized username/password; generic invalid-credentials result for unknown/invited/disabled/wrong-password. Issues a fresh cookie/context. Deliberate replacement of an existing session must carry the expected context.                         |
| `POST /api/auth/logout`                           | Revoke exactly matching current session, clear canonical/legacy cookies. If expected context mismatches, return 409 without touching the actual cookie.                                                                                             |
| `POST /api/auth/password`                         | Active cookie session, expected context, current password and new password; transaction rotates hash, invalidates all sessions, and issues a fresh current session/context.                                                                         |
| `POST /api/auth/logout-all`                       | Active cookie session/context; revoke all own sessions and clear cookie.                                                                                                                                                                            |
| `GET /api/admin/accounts`                         | Admin only; bounded/paginated list of user ID, username, display name, role, status, creation time, invitation expiry as applicable. No passwords, token hashes, session secrets, or other-user content.                                            |
| `POST /api/admin/accounts`                        | Admin creates invited member with username/display name; returns account plus a one-time invite token/expiry for the UI to construct a same-origin fragment link.                                                                                   |
| `PATCH /api/admin/accounts/:userId`               | Admin changes member display name or enabled state; rejects changes to user ID/username/role and cannot disable original administrator. Disable revokes all sessions and outstanding account tokens.                                                |
| `POST /api/admin/accounts/:userId/invitation`     | Reissue invitation for an unactivated member; revoke prior invitation atomically.                                                                                                                                                                   |
| `POST /api/admin/accounts/:userId/password-reset` | Admin issues one-time reset link for an activated member; old sessions/password remain until successful redemption unless admin separately disables/revokes. No plaintext password chosen by admin.                                                 |
| `DELETE /api/admin/accounts/:userId/sessions`     | Admin revokes all member sessions immediately without removing data.                                                                                                                                                                                |
| `POST /api/auth/invitations/accept`               | Public token plus user-selected new password; consume exact invite and activate once, then return to normal login (avoid automatic cross-account sign-in).                                                                                          |
| `POST /api/auth/password-reset/complete`          | Public token plus new password; atomically consume reset, replace credentials, revoke sessions, then return to normal login.                                                                                                                        |
| `POST /api/auth/owner-recovery`                   | Operator bearer only, with no account cookie; issue a short-lived reset token for the protected original administrator. No supplied user ID, no account listing, no browser control. Reject before first-account setup and apply bounded admission. |

Invite links should carry the token in the URL fragment, be read into temporary memory then removed using `history.replaceState`, and not enter localStorage, page caches, analytics, logs, query parameters, or request paths. A proposed initial expiry is 48 hours for invitations and 1 hour for resets. The administrator copies/shares the link manually; no external messaging integration. Generic malformed/expired/used-token responses are adequate; invited username/display name can be shown only after token validation if a preview endpoint is needed.

Own password change and member reset cover ordinary account maintenance. If the bootstrap administrator forgets its password, the explicit operator-only owner-recovery endpoint preserves recovery through the existing configured token and returns a one-time reset token. Its guard requires `authMethod: 'legacy-token'`, no cookie, and the original owner marker; it is not on the public auth allowlist. The browser receives no new bearer-token storage flow. Document the operator command without printing an actual deployment token.

## Authorization and legacy compatibility

Retain `READER_AUTH_TOKEN` (`API_AUTH_TOKEN` alias) as a high-privilege operator/legacy credential scoped strictly to the original owner. It must never select an arbitrary user ID or bypass owner predicates. Keep the present external-listener token requirement for this release to avoid an unrelated deployment change; tokenless authenticated deployments can be evaluated separately.

When a canonical/legacy account cookie is present, resolve that cookie and never fall back to the owner bearer on failure or disagreement. A request with no cookie may use the configured bearer and gets the fixed owner principal. Browser account mode stops attaching stored/build-time bearer tokens; existing desktop/API clients retain their owner access. A cookie session plus stale bearer cannot become admin. Current-session logout intentionally does not rotate the deployment secret; operator rotation remains a separate action.

Add role checks to `/api/admin/system` and `/api/admin/system/requests`, account administration, global operational metrics, and any server-wide network/component/install settings. Classify existing provider and source controls by actual storage scope: per-user settings stay available to their user; host-global actions require admin. Until a runtime/credential-backed route is genuinely user-isolated, deny it to members explicitly rather than reuse the owner instance. Do not ship such denial as a substitute for the requested per-user source credential support.

## Password/session protections within existing infrastructure

V1 retains Node 22's asynchronous scrypt, the existing `scrypt-v1` format and work factor for existing/new/changed passwords, and random salt/token generation. Bounded hashing admission is required; changing password cost or rehashing existing credentials is not part of this initial multi-account milestone. A separate measured follow-up can introduce scheme-aware stronger hashes and conditional rehashing after successful login. For that follow-up, OWASP lists N=16384, r=8, p=5 among its minimum scrypt configurations; Node documents the memory constraint and recommends a random salt of at least 16 bytes. This reference does not claim the current p=1 factor meets that recommendation. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Node 22 scrypt](https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

Preserve current password validation initially to avoid forcing existing owners to reset. Verify unknown usernames with a fixed dummy credential of the current scheme so account existence does not have a cheap early-exit path. Continue constant-time digest comparison. Before hashing, cap concurrent expensive auth operations and apply bounded IP plus normalized-account failure buckets; do not let success on a different account erase failures for the attacked account. Return Retry-After for throttling. Extend protection to token redemption and password verification. Keep a global admission bound against username/IP rotation. If API replicas are enabled, move the limiter behind shared Redis/database admission before claiming cross-instance limits; process-local limits alone have a known restart/replica limitation.

Keep opaque 32-byte session secrets, SHA-256 database lookup hashes, 30-day absolute expiry, and Secure/HttpOnly/SameSite=Strict cookie behavior. No JWT/OAuth replacement is needed. Session context is not accepted as authentication. Update `last_seen_at` at a coarse interval only if displayed; do not claim the existing column is accurate. Cleanup of expired sessions/tokens can reuse bounded existing auth maintenance rather than a new scheduler.

For unsafe cookie-authenticated requests, validate expected session context and an exact trusted browser origin; require JSON for auth/admin bodies. Use Origin and Referer fallback, rejecting cross-origin, `null`, or unverified missing origins for these flows; do not trust arbitrary X-Forwarded-* headers. Handle legitimate same-origin deployments/proxies through configured origins/trusted proxy settings and tests. Bearer-only native clients do not acquire ambient cookie authority and are separate from this browser-origin check. Initial setup/login/token redemption also need origin validation to prevent login/setup CSRF. SameSite remains an additional layer. [OWASP CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Invite/reset tokens use cryptographically random values, hashed storage, short expiry, atomic single consumption, and revocation; these reuse session-token primitives. Password reset never exposes or emails a password, and successful reset invalidates sessions. [OWASP password recovery](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

Reuse structured logging with safe auth/admin event names and non-secret result codes. Never log password, setup submissions, raw invite/reset token, cookie, Authorization, tokenized URL, or request body. Add tests for the new fields rather than broadening the deliberate first-owner setup-code logging exception. Administrator actions should record actor/target IDs in a small structured audit record if these IDs are needed; the current logger's safe-field policy otherwise redacts arbitrary strings.

## Delivery order and rollback boundaries

1. Add shared contracts, principal helpers, role checks and migration/service tests. Keep the account-create UI unavailable while static owner routes remain.
2. Apply an additive/controlled schema migration, preserve owner hashes/sessions/identities, implement multi-account lookup and the original-owner bearer mapping. Bootstrap races and changed DEFAULT_USER_ID must fail safely.
3. Convert every user route/service/worker/runtime boundary and browser cache/context boundary together. Make unsupported member routes fail closed during development. Verify same-file import and restore collisions under the separate isolation plan.
4. Implement invitation, member lifecycle, password and revocation service transactions, then wire the existing auth/settings UI and session-context enforcement. Add administrator-only server controls.
5. Run synthetic migrated-owner plus two-member acceptance tests in an isolated database and browser profiles. Only enable invitation creation in the delivered build when all boundaries pass.

Once multiple accounts exist, an older singleton application cannot safely run on the expanded schema. The deployment/updater must enforce a migration compatibility floor in its release manifest or equivalent upgrade/downgrade checks and refuse an incompatible older application. Do not rely on the old binary to recognize or enforce a constraint introduced by this release. Take an operator database/storage backup at actual deployment time, and rollback only with a matching application/database snapshot when crossing that floor. This planning task neither reads nor changes production state.

## Acceptance tests

- PostgreSQL migration test starts from the actual previous schema plus synthetic owner library, v1 hash, session, and plugin IDs. Upgrade preserves every owner ID/object/session; only the intended owner becomes admin. Fresh and token-only installations still attach bootstrap credentials to the seeded owner. Migration is repeat-safe through the ledger, and changed DEFAULT_USER_ID fails closed before seeding/serving a wrong owner.
- Simultaneous first setup produces one administrator; duplicate normalized Unicode usernames create one account. User/account/invite insertion is atomic and leaves no orphan on conflict. Existing plugin-account FKs survive primary-key changes.
- An invite can be redeemed once, expires correctly, is replaced/revoked correctly, and never works for a different purpose. Simultaneous redemption yields one success; disabled invited accounts cannot activate. Reset redemption cannot reopen disabled accounts.
- Three cookie jars resolve to three immutable owner IDs; bad/expired/disabled cookies return 401. Member cookie with the owner bearer stays member or is rejected; invalid cookie never falls back to bearer. Header/body user IDs and role spoofing have no authority.
- Member receives 403 on account lists/mutations, management updates/status and other global controls. Admin ordinary library queries remain scoped to admin's own library. No password/session/invite material occurs in listing/status/errors/logs/export.
- Old A request plus new B cookie gets 409 before reads/writes/queue admission. The same holds across A logout/login to a new A session. Mismatched logout cannot clear B's cookie. Direct media grants are scoped, expire, and stop after issuer-session revocation.
- Password change/reset/revoke-all/disable invalidate previous sessions and grants; re-enable does not resurrect them. Concurrent password verification/login with disable/reset cannot create a valid stale session. Original administrator cannot be disabled/deleted/demoted.
- Existing/new/changed passwords retain the v1 format and parameters; invalid-length handling, dummy verification, IP/account/global admission, 429 Retry-After, and no unbounded failure-map growth have focused tests. Use controlled hashing in ordinary unit tests and at least one real-scrypt integration case. Work-factor migration tests belong to the optional later upgrade.
- Deployment/updater compatibility tests reject an older singleton release against the expanded multi-account schema; rollback across the compatibility floor requires restoring the matching database snapshot rather than trusting old application startup behavior.
- Cookie flags, legacy-cookie migration, context bootstrap, allowed/denied/missing/null origins, reverse-proxy HTTPS, and bearer-only desktop compatibility are tested with Fastify injection plus a real-browser flow where browser header/cookie semantics matter.
- Browser runs invitation acceptance → login → separate library → logout → other account, including two tabs, expired session, disabled account, pending requests, offline/PWA artifacts, password reset, and old cached application reload. Client-specific details belong to the browser plan.

Existing focused starting points: `apps/server/src/auth.test.ts`, `routes/auth.test.ts`, `services/self-host-auth-service.test.ts`, `db/self-host-auth-migration.test.ts`, `db/migrate.integration.test.ts`, `management/server-management.test.ts`, `src/features/auth/self-host-auth-client.test.ts`, `SelfHostAccountGate.test.tsx`, and source/runtime ownership tests. New database tests must execute real SQL constraints/transactions; migration text assertions alone are insufficient. Run the server/frontend type checks and the affected integration/browser suites using available `node_modules/.bin` tools; no production database or external credentials are needed.
