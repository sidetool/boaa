# Self-host multi-account data and runtime isolation

Read-only implementation planning against `release/server-beta4`, commit `c681f97` (2026-10-18). Scope: administrator-created accounts/invitations for family and friends, separate libraries and source logins, self-host web/PWA. Desktop behavior is outside this change. This document covers server/data/runtime boundaries; account/session and client designs are companion work.

No production data, mounted private providers, private extensions, or secrets were inspected. Paths below refer only to site-neutral repository code. No implementation, migration, deployment, or external transfer was performed.

## Decision

Keep one server, database, object backend, Redis queues, and set of runtime binaries. Make each authenticated account the owner of its library, source bindings/state, and jobs. Administrators approve/provision executable source packages; members control their own enablement, preferences and logins. Introduce explicit immutable owner context at service boundaries and lazy owner-scoped runtime instances. Do not mutate `config.defaultUserId` while serving a request and do not register a second full set of routes for each account.

Retain the existing default user's ID, records, encryption key, object keys, and hashed runtime directories. It becomes the initial administrator. `DEFAULT_USER_ID` remains a bootstrap/migration compatibility input, never an authorization fallback for an ordinary request or background job.

Server administrator privileges control shared infrastructure. They do not implicitly switch a request into another account's library or expose another account's source credentials. Existing environment credentials remain administrator-only unless an administrator explicitly enables a shared provider service.

`server.ts` is the composition hotspot; route and service changes are also needed throughout `routes/books/`, `routes/ai/`, `routes/sync/`, `services/book-ai-workflow/`, backup/import services, and provider factories. A mechanical replacement of `defaultUserId` is insufficient for the ID-only and in-memory paths below.

## Release-blocking leakage/corruption paths

1. **Upload ID alone grants control today.** `routes/uploads.ts:108` loads progress by upload ID; chunk writes around line 312 and cancellation around line 394 lock an ID without `user_id`. Completion and import-job polling need the same audit. Another account must not read status, append chunks, finish, retry, cancel, or clean up that upload. Query and lock `(id, owner)` before touching chunks or files; return the same missing response for foreign and nonexistent IDs.

2. **Identical or supplied IDs can overwrite another library.** `db/schema.sql` has global primary keys for books and descendants. `import-service.ts:459` derives a comic book ID from content, line 649 derives an object ID from raw hash, lines 843–857 replace the globally deduplicated object's key/metadata, lines 875–903 upsert a book without an owner guard when `expectedBase` is absent, and lines 971–1014 select/upsert asset IDs globally. Expected-base checking is optional (`services/import-expected-base.ts`). Fix all these before allowing a second library; filtering list APIs does not stop this mutation path.

3. **Runtime state and temporary capabilities belong to the default owner.** `routes/extension-packages.ts:119–138` creates one catalog/registry/cache owner; prepared images/documents each allocate one artifact store; APK streams live in the catalog. `routes/backups.ts:49–70` shares staging/download tickets and operation flags. `routes/request-progress.ts:6` indexes a caller-supplied ID without an owner. A member must never consume, cancel, overwrite progress for, or discard another account's handle, even when the handle is known.

4. **Background execution can select the wrong account.** `worker.ts` uses one server config, while provider dispatch and workflow services obtain owner from its default ID. Import execution accepts `jobId` and `uploadId` separately; `import/source-reader.ts` loads the upload by ID. Persisted jobs, attempts, uploads, workflows, books, and credential owners must agree before execution; recovery must work for every enabled account. Queue payloads cannot choose an owner or authorize foreign work.

5. **Legacy external sessions are shared.** `routes/webnovel-metadata-collector-gateway.ts:206` injects a single collector token, including browser frame/action/session endpoints. `services/runtime-components/metadata_runner.py` creates one `ProviderContext(data_dir)` and one provider application. `routes/text-source-gateway.ts` similarly closes over one companion token or installed catalog. Passing a new user header alone does not isolate an upstream's global cookies, caches, browser frame, or filesystem.

6. **Global management has authentication but no role check.** `management/server-management.ts` exposes updater status/requests behind the ordinary auth hook; `routes/source-network-settings.ts` exposes the shared default and process control. Explicit server-side admin guards are required before member accounts exist. Hide privileged controls in the client as a separate usability change.

## Implementable service contracts

### Request and repository ownership

Use the authenticated principal from the identity work to supply `OwnerContext { userId }`. Pass it explicitly to personal service/repository operations. Keep `ServerConfig` for deployment settings; do not create a mutable process-wide “current user.” A short-lived adapter can construct an immutable owner-bound service object while signatures are migrated, but no route should silently inherit a bootstrap owner.

The identity work supplies `{ userId, role, authMethod }` and a server-validated opaque session-context fence for cookie web requests. Check the fence before reading/mutating personal state so a stale A tab cannot submit work using a newly logged-in B cookie. The fence identifies the authenticated context; it does not accept a browser-selected user ID. Legacy bearer access stays bound to the original owner.

Use centralized owned-resource loaders for books/chapters/assets, uploads/jobs, and ephemeral capabilities. Child records without a `user_id` remain valid only when reached through a verified owned parent. Add composite ownership constraints where parent and child both carry owner columns: e.g. `(upload_id, user_id)` and `(book_id, user_id)`. Reject mismatched relations rather than relying on separate foreign keys that only prove both rows exist.

Use explicit per-owner predicates and database constraints for this release. Row-level security could be additional defense later, but it is not a substitute for object/worker/runtime isolation and should not expand the first rollout into a pool-session-state rewrite.

### Resource identities and stored objects

Preserve existing admin resource IDs. For a new hosted import, allocate a server-owned ID in an account namespace and derive/remap the entire content graph from it. A `clientBookId` used for replacement or append must resolve to a book owned by that account. A proposed new client identity is an owner-scoped alias/idempotency key, not permission to choose a global database key.

Prefer a durable mapping from `(owner, source identity)` to hosted book ID to preserve retries and duplicate-import behavior. Extend the existing rekey/import machinery to cover TXT, EPUB resources, fixed documents, image/document series, revisions, annotations, and nested references. `services/import/rekey.ts` currently rekeys text chapters/paragraphs only; it is not a complete graph remapper. Preserve content hashes; do not redefine global cross-platform content identity rules for the desktop application.

Add `book_objects.user_id`, backfill the legacy administrator, and replace raw-hash uniqueness with `(user_id, raw_text_hash)`. Derive new object IDs from owner and content hash. Preserve old object IDs/storage keys; existing file-store hashes remain readable. This avoids mutable cross-account deduplication and its key/filename/cleanup coupling. A later immutable content-addressed store could share bytes with explicit reference accounting, but is unnecessary here.

Always fence `ON CONFLICT` mutation with the existing row's owner, including book assets and user fonts. Apply the same rule to client-generated annotation IDs, operations, shelves, jobs, and restore rows. Scope sync replay/event uniqueness by owner. V1 rejects cross-account archive transfer and hides/disables member restore; it does not attempt a partial graph remap. Existing admin restore must preflight and reject foreign-owned IDs/references without changing them. A later owner-safe transfer feature must remap every imported entity/reference before persistence; own-account replacement can retain its explicit conflict workflow.

Object storage remains one private bucket/directory. New keys include the owner; APIs derive keys from owned metadata and do not accept arbitrary keys/paths. Existing keys are retained even if legacy layout differs. `services/object-delete-outbox.ts` already rechecks references across object/asset/font/TTS/review tables before deletion; retain that global safety check and ensure candidates originate from owner-authorized changes. Scheduled cleanup is an internal global operation; user-triggered cleanup is owner-scoped.

### Owner runtime registry

Extract composition from `server.ts` into an `OwnerRuntimeRegistry` keyed by immutable user ID. It lazily creates/coalesces one owner bundle containing package store/catalog/registry, credential vault, configured content-service bindings, APK host, Mangayomi host, and prepared-artifact stores. Routes register once and request a bundle using the principal. No request body/query parameter chooses the owner root.

Use the existing directory layouts so the administrator's installations need no move:

- `extension-credentials/<sha256(userId)>`
- `apk-extensions/<sha256(userId)>`
- `mangayomi-extensions/<sha256(userId)>`

New backup staging can use a hashed owner subdirectory. Existing upload directories can remain keyed by server-generated unique upload IDs because DB ownership is verified before filesystem use. Keep encrypted state and installed code outside served/static/build paths.

Give every memory entry an owner boundary: catalogs, request deduplication, stream/page/cover caches, prepared image/document receipts, backup tickets, staging, progress, pending cancellations, and installation review plans. A per-owner instance is sufficient where practical; shared maps use `(owner, handle)` keys. Scope capability consumption and deletion as well as creation. Bind long-lived user-facing work to an account generation so disabling an account cancels its network requests and disposes its runtime state without affecting others. Normal logout removes session capabilities; durable account-owned jobs can continue unless explicitly cancelled.

Bound active owner bundles and global resource concurrency, and evict only idle bundles after closing workers/streams and persisting state. Existing APK per-catalog worker limits multiply by account, so retain a server-wide cap in addition to per-owner admission. This needs a small bounded pool, not one Docker deployment per member.

`SourceWebViewHost` is a process singleton, but already creates a fresh browser context for each evaluation and reads/writes cookies through the supplied vault. Its engine processes may stay shared. Extend its admission/serialization key with owner identity: current `scope.key` identifies package/source/epoch only. Keep storageState, cookies, local storage, user-agent history, live contexts and cancellation owner-bound. `services/runtime-components/browser-worker.mjs` remains an internal authenticated execution service; do not expose its runtime token or websocket capability to member clients.

APK JAR/runtime builds and browser binaries are shared administrator-managed infrastructure. Installed owner bindings, APK JVM workers and their in-memory cookie jars, encrypted preferences, and Mangayomi source state are private per account. An administrator update/removal of one binding invalidates only that binding's owner generation; server-wide revocation explicitly affects all bindings. Global source-network policy is injected separately from the owner vault; do not create a ByeDPI process controller per owner or stop it when an owner bundle is evicted.

### Executable packages: administrator approval, private bindings

For V1, guard installation/inspection/update/removal of executable APK, JS and plugin packages with admin permission. A member cannot upload executable code or select an arbitrary repository to run on the shared host. Allow members to toggle their own provisioned sources and change their own preferences/logins. Host-enforced enablement policy may still disable a revoked package for everyone.

Do not expose the existing administrator store/catalog as a shared catalog instance: `extension_packages` mixes archive bytes with owner settings/source state, and APK/Mangayomi roots mix archives with inventory, activation and preference state. Changing only route permission leaves those private fields shared.

The smallest safe rollout retains owner-local install records and roots. An explicit admin provisioning service copies only a verified executable/manifest/digest and approved host grants into a target owner's clean binding, generating fresh activation/credential epochs and empty settings/source state. Never copy vault files, source preferences, credentials, stream handles or cache data. Member accounts start without provisioned packages. Updates/removal are administrator operations that act on selected bindings and invalidate each affected owner runtime separately.

This initially duplicates immutable code bytes. A later normalization can add an administrator-owned immutable artifact catalog and owner bindings referencing its digest; installation inventory can then be shared read-only while enabled state, revision, preferences and all runtime state remain per owner. That change requires archive resolution support in `PostgresPackageInstallStore`, `ApkInstallations`, and `MangayomiExtensionHost`; it is not achieved by reusing the administrator's current host. Either storage representation is compatible with bounded lazy owner contexts and no JVM allocation merely for registering an account.

## Global service policy and companion cut

Admin-only: executable package provisioning/update/removal, updater requests/status details, runtime enablement/version/update, ByeDPI lifecycle/default proxy, private-origin policy, upstream endpoints/tokens, object/DB/Redis configuration, provider master key, aggregate diagnostics/metrics, and administration of invitations/accounts. Members may receive a safe capabilities projection without internal endpoints, token hints, or other owners' details.

Per owner: library/reader/integration/discovery choices, provisioned source bindings and enablement, source preferences and login secrets, browser sessions, provider settings and user API keys, provider jobs/results, and backup/sync state. Administrator repository management is separate from those bindings. Existing provider secret encryption already includes the owner in AAD. New source-vault envelopes should include owner in their authenticated scope/key derivation; retain a versioned legacy reader only in the preserved admin directory and upgrade on write without copying secrets to new accounts.

Environment LLM/TTS/content credentials represent operator services. Preserve existing behavior for the legacy admin; do not automatically grant new members access or expose credential status hints. If enabled as a shared service, expose a capability, enforce the existing per-user provider admission plus server capacity limits, and use that service's credentials only for authorized jobs. Local provider endpoint/file-path credentials remain administrator configured; arbitrary member-supplied server credential paths are not personal credentials.

For metadata, implement a versioned managed-runtime owner capability: server-derived opaque owner key in authenticated internal requests; per-owner data directory and provider context/app or separately isolated process; owner-aware caches/browser controls; disposal on account disable. Protocol capability negotiation must fail closed when the runtime cannot provide isolation. Existing provider app globals cannot be repaired merely with a context variable; code that keeps global login state requires per-owner process/app isolation or an audited owner-aware provider contract.

The first release may keep the existing external metadata/text companion login and authenticated content routes administrator-only, with a clear member capability-unavailable result. Public metadata operations may be shared only after proving their results/state do not use admin login. Owner-isolated installed extension sources can be available independently. Complete member metadata login support in the companion phase without reading/modifying private provider code during this public host change; coordinate any separately authorized provider adaptation in its private workspace.

## Practical phase cuts

1. **Owner infrastructure and role gates, still one enabled account.** Land principal/owner contracts with the identity work, admin checks for global controls, owner-aware repository interfaces, central ownership loaders, additive schema constraints and ID allocation. Restrict legacy companion capabilities. Keep invitations unavailable until the next phases' isolation tests pass.

2. **Library, jobs, personal export and sync isolation.** Convert book/shelf/read routes and every member-enabled AI service, close upload ID-only paths, namespace new import identities and objects, scope sync replay, and bind tickets/progress/staging. Workers load owner from the database and verify job/upload/book/attempt relationships; reconciliation iterates owner-bearing rows rather than assuming the bootstrap account. Test two concurrent owners using the same source bytes and deliberately reused IDs. Gate optional AI/restore paths that cannot yet meet these rules instead of sharing the admin context.

3. **Source runtime isolation and member release.** Introduce the bounded runtime registry, separate owner stores/vaults/APK/Mangayomi workers and ephemeral artifacts, administrator package provisioning with fresh owner bindings, keep global network/process control admin-only, and integrate client account/cache switching. Enable invitations only when the two-account suite covers every member-enabled route. Legacy metadata/text companion auth remains admin-only until phase 4, while supported owner-scoped sources work normally.

4. **Managed companion multi-owner support.** Add owner-capability negotiation and isolated metadata/provider state, verify frame/action/cookie/cache boundaries with a synthetic provider, and then expose member login. External single-owner companions remain explicitly admin-only unless they implement the contract.

Each phase is reviewable separately, but phases 1–3 form the minimum safe member-account release. Do not ship a partially converted route set behind an enabled invitation UI.

The V1 member gate requires private library/import/download/read state, provisioned source login/preferences/browser state, account switching, and owner-safe personal backup export to work. Explicit V1 exclusions are arbitrary executable package/repository mutation, updater/global configuration, current external collector/text-companion authenticated sessions, server-wide restore, member backup restore/cross-account archive transfer, and use of ungranted global provider credentials. Any other optional AI/integration route that is not yet owner-bound is omitted from the member capability response/UI and returns `403` if called directly. There is no direct-network fallback, default-owner fallback, or silent use of administrator credentials. Shared artifact storage and companion login isolation are subsequent work, not invitation-release prerequisites.

## Migration that preserves the current server

1. Rehearse against generated fixtures containing the legacy account, representative books/assets/revisions, source-vault fixtures, installed synthetic packages, and queued jobs. Never copy production/private extension data into tests or public artifacts.
2. Before the actual upgrade, use the established operator backup procedure for DB, object volume, data directory/master key, runtime state volumes and updater state. Account library ZIPs intentionally omit auth/runtime credentials and cannot replace a server rollback backup. This planning task does not perform that backup or upgrade.
3. Enter server-wide maintenance and drain/stop API writes, provider/import workers and runtime work before schema cutover. The existing updater activity/queue checks are relevant, but runtime requests and owner bundles also need accounting. Preserve recovery semantics for interrupted queued jobs.
4. Convert the singleton account while retaining its exact `user_id`; do not recreate `users` or change `DEFAULT_USER_ID`. Attach all legacy ownerless source objects to that owner, validate existing child-owner relations, and add constraints only after validation. An unexpected second owner/shared object is a migration error requiring explicit reconciliation, not a mass reassignment.
5. Keep all object storage keys, bucket selection/legacy fallback, encryption master key, encrypted source directories, APK preferences keys, Mangayomi state, library IDs, and sync sequence values. New accounts start empty. Record the preserved legacy runtime owner in migration metadata so later environment edits cannot redirect ownership.
6. Load new runtime bundles lazily. Migrate the source-network default from the legacy vault into a dedicated global settings store through a one-time validated copy; leave the legacy payload/key intact for rollback. Do not scatter it into member vaults. New source-vault envelope versions must read preserved legacy admin state without changing existing plaintext semantics.
7. Verify the admin sees the same counts/content, secrets still decrypt, old object keys read, queued jobs recover under the right owner, and a new member starts with no private state. Only then leave maintenance and allow invitations. Rollback after member writes requires restoring the coherent pre-upgrade DB+volume snapshot; merely reverting application binaries is unsafe.

## Acceptance evidence

Use real PostgreSQL integration fixtures where ownership, conflicts and foreign keys matter, plus fake provider/browser transports and temporary file-object stores. A mocked query test alone cannot demonstrate isolation. Extend existing route/import/backup/runtime tests; avoid real paid providers, external logins, and production/private data.

- Two accounts A/B concurrently import identical TXT/EPUB/fixed-document/image-series bytes; replace/append/reimport/delete in A; B's book content, assets, original bytes, titles, read state and storage remain intact. A supplied foreign book/asset/revision ID is rejected without mutation. Verify all descendant and nested references after import rekey.
- Cross-account known-ID requests cover book/chapter/page/text/search/cover/original/font/TTS assets, shelves/annotations/reading state, upload status/chunk/complete/cancel/retry, jobs/workflows/results, backups and sync. Missing/foreign resources do not disclose titles, status, errors, or payloads. Administrative role alone does not change the personal owner.
- A/B enqueue imports and provider jobs with distinguishable fake secrets; run/retry/recover them interleaved. The worker uses the persisted owner and correct secret. A mismatched job/upload pair and stale/foreign attempt fail before content or provider execution. Disabling A stops A's new dispatch/runtime access without stopping B.
- A/B use the same synthetic package/source ID and same credential epoch with different preferences/cookies. Listings, updates, authentication, HTTP/browser results, local storage, caches, prepared receipts, stream tokens, progress and cancellations remain separate. Disable/remove A's package and confirm B is unaffected; verify across process restart.
- Replay A's backup ticket/staged ID/progress ID/prepared receipt/stream token as B; it cannot return or delete A's content. Personal export contains only the caller's synthetic library. Member restore/transfer returns the advertised unavailable/forbidden response; existing admin restore rejects foreign-owned identities and cannot introduce accounts, role changes, credentials or runtime installations. Full cross-account restore/remap tests belong to the deferred transfer feature.
- A/B submit identical client event IDs and device labels. Each receives only its own sync events and its own idempotency result; a foreign chapter/paragraph/annotation reference cannot be attached to an owned book. Per-owner settings/peer/cursor state does not reset or advance another owner.
- Member requests to updater, runtime/global network controls, internal diagnostics and legacy logged-in companion routes are denied server-side. Managed metadata owner support tests use a synthetic provider with per-owner cookies/files/browser frames and reject omitted/forged/unnegotiated owner context.
- Member executable installation/update/removal is denied. Administrator provisioning of the same synthetic package to A/B creates independent bindings without copying any settings/cookies; changing A's preferences/enablement leaves B unchanged. Shared immutable code, if introduced, cannot change without an administrator-approved digest update.
- The legacy migration fixture retains IDs, DB counts, object bytes/keys, source/provider decryption, package enablement and pending job behavior; a fresh installation and new member start clean. No changes are made to desktop identity behavior.

After implementation run the server TypeScript build and the repository's targeted route/integration/runtime test commands. Expand to existing import/backup/sync regression suites because this change touches identity and storage. This planning review did not run implementation tests.
