# 관리자 초대 방식의 다중 계정 구현 계획

상태: **첫 버전 구현 완료, 운영 미배포**. 기준 코드는 `c681f97`이며 작업 브랜치는 `feat/admin-invited-accounts`다. 기존 `release/server-beta4`의 UI 수정 위에서 분기했다. 코드의 초대 기능은 활성화했으며 운영 서버와 데이터는 변경하지 않았다. 아래 검증 한계와 원인 미확정 항목은 남아 있다.

사용자가 선택한 방식은 관리자가 가족·지인 계정을 만들고 초대하는 방식이다. 초기 검토는 Astra xhigh로 나눴고, 인증·데이터·클라이언트 동작 구현은 Astra medium, UI/UX는 Opus 5.5 medium으로 진행했다. 독립 검토에서 재현된 결함을 수정한 뒤 사용자의 할당량 요청에 따라 추가 xhigh 검토는 중단했다. 마지막 검증은 실제 앱·서버의 핵심 흐름과 변경 파일 정적 검사에 한정한다.

## 사용 방식

1. 기존 계정은 같은 ID와 서재를 유지한 채 관리자가 된다. 새 서버는 현재처럼 최초 관리자 설정을 한 번 진행한다.
2. 관리자가 아이디·표시 이름을 정해 회원을 만들고, 일회용 초대 링크를 복사해 직접 전달한다. 공개 회원가입이나 이메일 발송 서비스는 추가하지 않는다.
3. 초대받은 사람은 자기 비밀번호를 설정한 뒤 로그인한다. 새 계정의 서재·기록·소스 로그인은 비어 있으며, 관리자 자료를 자동 복사하지 않는다.
4. 관리자는 회원의 이용 중지·재활성화, 초대 재발급, 비밀번호 재설정 링크 발급, 세션 해제를 할 수 있다. 회원 비밀번호나 소스 로그인 정보를 보는 기능은 만들지 않는다.
5. 첫 버전은 서버 웹/PWA를 지원한다. 같은 브라우저 프로필에서 계정을 바꾸면 쿠키를 공유하는 다른 탭/PWA도 재확인한다. 탭마다 다른 계정을 동시에 유지하는 기능과 데스크톱 계정 UI는 범위 밖이다.

서버 운영자가 DB와 파일에 접근할 수 있다는 사실까지 숨기는 암호화형 서비스는 아니다. 여기서 보장하는 분리는 앱/API 및 실행 상태의 계정 경계다.

## 코드 검토에서 확인한 주요 작업

- **로그인 통과와 소유자 선택이 분리돼 있다.** 현재 인증은 요청을 허용할 뿐, 요청에 사용자를 붙이지 않는다. 여러 라우트·서비스는 `defaultUserId` 한 명을 사용한다.
- **목록 필터만 바꿔서는 부족하다.** 업로드 일부 경로는 ID만 검사한다. 동일 파일의 전역 ID와 충돌 시 갱신 경로는 두 계정의 데이터를 덮어쓸 수 있으므로, 가져오기·하위 자료·원본 파일까지 확인해야 한다.
- **소스 실행 상태가 한 사람에게 묶여 있다.** 확장 호스트·암호화 보관함·쿠키·임시 스트림/백업 토큰을 요청 사용자에 맞게 선택해야 한다.
- **브라우저도 로그인 화면 밖에서 상태를 공유한다.** 현재 앱 실행 객체가 로그인 전에 만들어지고 재사용된다. 일부 IndexedDB·자격 증명·표지 캐시와 이전 로컬 상태 가져오기 역시 계정별 경계가 필요하다.
- **다른 탭의 쿠키 변경이 먼저 일어날 수 있다.** 탭 간 알림만으로는 이전 계정의 저장 요청을 막을 수 없다. 서버가 요청의 예상 세션과 실제 쿠키 세션이 같은지 확인해야 한다.

이 내용은 다중 계정을 추가할 때 해결해야 하는 경계다. 현재 단일 계정 운영에서 다른 회원의 데이터가 이미 유출됐다는 판정은 아니다.

## 구현 순서와 완료 조건

| 단계                          | 구현                                                                                                   | 해당 단계의 완료 조건                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 1. 인증 계약과 기존 계정 이전 | 사용자/역할을 가진 요청 주체, 다중 계정 스키마, 기존 관리자 보존, 관리자 API 권한 검사                 | 이전 스키마에서 관리자 ID·세션·서재·플러그인 ID가 보존되고, 회원이 관리자 API를 호출하지 못함 |
| 2. 서재·파일·작업 소유권      | 사용자별 조회/쓰기, 업로드 소유권, 신규 ID 구분, 백업/동기화 경계, 작업자 소유자 전달                  | A/B가 같은 파일과 요청 ID를 사용해도 가져오기·삭제·재시도·내보내기에서 서로 영향 없음         |
| 3. 소스와 실행 환경           | 필요할 때 여는 사용자별 실행 객체, 관리자 승인 코드 배포, 별도 로그인/쿠키/임시 토큰, 공통 실행량 제한 | 같은 합성 소스의 A/B 로그인·설정·브라우저 결과가 재시작 후에도 분리됨                         |
| 4. 브라우저 계정 수명         | 인증 후 앱 구성, 요청별 예상 세션, 계정별 저장소/캐시, 로그아웃 정리, 다중 탭 처리                     | 늦은 A 응답과 저장 요청이 B의 화면·저장소·서버에 반영되지 않음                                |
| 5. 초대와 관리 UI             | 계정 목록·초대·비밀번호 설정/변경·중지·재발급, 권한에 맞는 설정 화면                                   | 관리자 초대부터 회원 독서·로그아웃·다른 계정 로그인까지 실제 브라우저로 연결됨                |
| 6. 독립 검토와 배포 준비      | 실제 PostgreSQL 이전/격리 테스트, 두 계정·두 탭/PWA 검증, 기존 기능 회귀, 이전 버전 복귀 제한          | 필수 격리 검증을 모두 통과한 빌드에서만 초대 기능을 활성화함                                  |

1단계 계약을 먼저 정하고 서버 데이터, 소스 실행, 브라우저 수명을 파일 소유권으로 나눠 구현한다. 초대 UI를 먼저 열고 뒤에서 데이터 분리를 보완하는 순서는 사용하지 않는다. 미격리 선택 기능은 서버에서도 명시적으로 거부하고 화면의 지원 범위에 반영한다.

공유 수정 지점인 `server.ts`, DB 스키마/마이그레이션 번호, 공통 인증 타입은 한 담당자가 통합한다. 기존 UI 결함 수정과 개인정보 격리 변경을 한 번에 다시 설계하지 않는다.

## 공통 계약

- 요청 주체는 서버가 확인한 `{ userId, role, authMethod }`다. 요청 본문의 사용자 ID나 역할은 권한 근거가 아니다. 공통 설정의 `defaultUserId`를 요청 중 바꾸지 않는다.
- 인증 응답은 기존 배포의 `serverId`, `libraryId`, 매핑된 플러그인 `accountId`, DB의 `account.userId`, `sessionContext`를 제공한다. 기능 지원 목록과 기존 로컬 자료 이전 자격도 서버가 명시한다. 이름을 바꿔도 저장소 소유자는 바뀌지 않는다.
- 쿠키 기반 요청에는 `X-BOAA-Session-Context`를 붙인다. 실제 세션과 다르면 `409 session_context_mismatch`로 거부하고 새 계정으로 자동 재시도하지 않는다. 이 값 자체는 로그인 수단이 아니다.
- 상태/세션 조회는 현재 세션을 알아내는 예외다. 로그아웃도 예상 세션을 검사하여 이전 탭이 새 계정의 쿠키를 지우지 못하게 한다. 직접 이미지/미디어/다운로드 요청은 소유자가 확인된 fetch 또는 세션에 묶인 제한된 이용권으로 처리한다.
- 초대/재설정 토큰은 DB에 해시로 보관하고 만료·재발급·일회 사용을 원자적으로 처리한다. 링크의 fragment에서 읽고 URL에서 제거한다. 초대 수락 자체는 자동 로그인하지 않으며, 다른 계정이 로그인돼 있다면 명시적으로 로그아웃한 뒤 진행한다.
- 기존 운영용 bearer 토큰은 기존 관리자만 가리킨다. 쿠키가 있는데 잘못됐다는 이유로 관리자 bearer 인증으로 바꾸지 않는다. 웹 계정 모드에서는 예전 공통 bearer를 요청에 자동 첨부하지 않는다.
- 기존의 계정 구분 없는 브라우저 저장소는 원래 소유 서버를 입증할 수 없어 자동 이전하지 않는다. 기존 자료는 삭제하지 않고 분리 보존하며 서버의 개인 설정을 새 계정 저장소로 가져온다. 기기에만 저장됐던 외부 연결·폴더 권한은 다시 연결해야 할 수 있다. 처음 로그인한 회원에게 예전 로컬 데이터를 넘기지 않는다.

정확한 API·스키마·인증 동시성 규칙은 [인증 설계](multi-account-identity.md)를 따른다. 클라이언트와 서버의 계약이 다를 때는 구현 전에 공유 타입에서 하나로 정한다.

## 성능과 범위 제한

계정마다 Docker·DB·Chromium 설치를 새로 만들지 않는다. 실행 바이너리와 서버 자원은 공유하며, 개인 상태를 분리한다. APK 등의 사용자 실행 객체는 사용할 때만 만들고, 서버 전체 실행 수와 유휴 정리를 함께 제한한다. 회원을 만들었다는 이유만으로 JVM을 실행하지 않는다.

첫 버전은 기존 계정의 파일·암호화 키·경로를 보존한다. 새 계정의 같은 파일은 사용자별 소유권으로 저장하므로 저장 용량은 사용한 자료에 따라 증가한다. 확장 코드도 첫 버전에서는 계정별 설치 상태에 복사할 수 있다. 공통 불변 코드 저장소와 계정 간 파일 중복 제거는 후속 최적화이며, 이번 격리 작업의 전제 조건으로 만들지 않는다.

기존 비밀번호 해시 형식을 유지하고, 인증 작업의 실행량 제한을 검증한다. 새 인증 서비스·OAuth·메일 서버·조직 관리·공유 서재·관리자 위임·계정 영구 삭제·계정 간 백업 이전은 이번에 추가하지 않는다. 성능에 영향이 없다고 미리 단정하지 않고 기존 관리자와 두 회원의 읽기/표지/로그인 경로를 비교한다.

## 검증과 운영 이전

- 합성 관리자와 회원 A/B를 쓰는 실제 임시 PostgreSQL로 이전·충돌·트랜잭션을 검증한다. 같은 콘텐츠, 알 수 있는 상대 ID, 같은 이벤트 ID로 조회와 변경을 시도한다.
- 실제 브라우저에서 초대 → 로그인 → 서재/다운로드/소스 사용 → 로그아웃을 연결한다. 두 탭에서 쿠키 변경과 늦은 요청을 교차하고, 탭 복원·오프라인·PWA 캐시·재접속을 확인한다.
- 기존 관리자 서재/기록/소스 암호 해독이 보존되는지, 회원이 관리자 전용 API나 공유 외부 로그인에 직접 접근할 수 없는지 검사한다.
- 타입 검사와 변경 경계의 테스트를 먼저 실행하고, 가져오기·동기화·독서·확장 회귀와 프로덕션 빌드를 이어서 확인한다. 코드 리뷰를 통과한 뒤 불필요하게 같은 전체 검사를 반복하지 않는다.
- 운영 이전은 검증된 빌드의 별도 단계다. DB와 원본/서버 데이터 볼륨을 함께 백업하고 쓰기·작업을 정리한 뒤 이전한다. 이전 단일 계정 바이너리만 다시 띄우는 복귀는 허용하지 않는다. 업데이트 경로가 스키마 호환 하한을 검사하거나, 맞는 DB/볼륨 백업과 함께 복원해야 한다.

위 검증 목록은 설계 요구사항이며 모두 실기로 확인했다는 뜻은 아니다. 구현 중 통과한 증거와 미검증 범위는 아래 기록을 따른다. 운영 자료는 조회하거나 변경하지 않았다.

## 구현 중 확인한 증거와 제한

- 실제 Fastify 서버, 임시 PostgreSQL/Redis, 전체 Vite 앱과 Chromium으로 관리자 초기 설정 → 초대 → 비밀번호 설정 → 회원 로그인 → HTTP 업로드와 실제 가져오기 → 개인 서재 표시 → 회원 권한 제한 → 같은 세션의 입력 보존 → 두 탭 계정 전환 → UI 로그아웃과 원래 계정 복귀를 확인했다. 390px 회원 계정 화면의 가로 넘침과 불필요한 서버 provider 호출도 검사했다. 명령은 `env -i HOME="$HOME" PATH="$PATH" BOAA_APK_RUNTIME_ENABLED=0 node apps/server/node_modules/tsx/dist/cli.mjs scripts/smoke-multi-account-browser.mjs`다. 테스트가 자기 임시 데이터베이스·컨테이너를 만들고 정리하며 기존 데이터베이스 환경 변수는 거부한다.
- 최종 실행은 시험용 활성화 옵션 없이 기본 `buildServer(config)`를 사용해 9개 흐름과 uncaught 오류 검사를 모두 통과했다. 이후 서버 production 검증, 웹 번들 생성과 변경 파일 포맷 검사를 통과했다. 이 검증은 실제 브라우저와 서버를 사용하지만 업로드 처리는 동일 프로세스에서 실제 import service를 호출하며 별도 BullMQ worker 컨테이너를 띄우지는 않는다.
- 전체 앱 검증에서 발견한 StrictMode 회원 목록 정지와 초대 토큰 소실은 수정 후 실제 화면에서 정상화됐다. 토큰은 주소에서 즉시 지우고 페이지 메모리에만 유지하며 수락/무시 후 제거한다. 모바일 화면 검사는 Chromium 에뮬레이션으로, 실제 휴대폰 키보드 검증은 아니다.
- 실제 임시 PostgreSQL에서 마이그레이션, 교차 계정 가져오기·동기화·독서 기록·백업 충돌을 검사했다. 독립 검토에서 발견한 4개 데이터 경계 결함은 수정 전 재현과 수정 후 차단을 확인했다. 자세한 내용은 [서버 검토](../reviews/multi-account-server.md)를 따른다.
- 로그아웃 응답은 세션 폐기만 수행하고 다른 탭의 새 로그인 쿠키를 만료시키지 않는다. 실제 Chromium에서 지연 응답 뒤 B 세션이 유지되는 것을 확인했다. 같은 세션 재확인은 앱을 유지하고, 다른 세션이나 만료일 때 실행 객체를 교체한다.
- 회원의 소스 다운로드 결과가 서버의 최종 책 ID를 따르도록 보완했다. 다음 묶음·추가 회차·재가져오기 및 확인된 결과 복구를 포함한 39개 집중 테스트가 통과했다. 서버가 완료했어도 클라이언트가 결과를 받기 전에 종료되는 경우 자동 연결 복구는 아직 지원하지 않으며, 모르는 결과를 추측해 다른 책을 연결하거나 지우지 않는다.
- 새 계정의 글꼴 ID와 FontFace 캐시를 계정별로 분리했고, 로그아웃 때 등록한 글꼴과 늦은 응답을 정리한다. 기존 관리자와 로컬 서재의 ID는 보존한다.
- **원인 미확정 잔여:** 처음 여는 두 번째 탭의 로딩과 세션 폐기를 겹친 한 실행에서 `signal is aborted without reason` 브라우저 오류가 2개 기록됐다. 그 실행에서도 계정 경계와 모든 화면 흐름은 통과했지만 uncaught 오류 검사는 실패했다. 스택 수집을 추가한 동일 흐름의 후속 두 실행은 오류 없이 통과했다. 취소·초기화 호출지점에서 확실한 원인을 찾지 못했으므로 추정 수정이나 오류 무시는 하지 않았다. 이를 해결된 결함으로 간주하지 않으며, 다음 재현 때 호출 스택을 기준으로 보완해야 한다.
- 웹·서버·스크립트 타입 검사, 변경 파일 lint(경고 0), 포맷, CSS/공유 계약/미추적 파일을 포함한 공개 경계, 웹 빌드와 서버 production 검증이 통과했다. hosted 구성 검사는 303개 항목을 통과했다. 파일 크기 검사는 AccountPage·Gate 등 책임 분리 후보를 알렸으며, 기능 검증과 무관한 대규모 재구성은 이번에 추가하지 않았다.
- 실제 APK/JVM의 다중 계정 동시 실행, 실물 모바일/PWA의 백그라운드 복원, 운영 백업으로 하는 epoch 전환 리허설은 이번 구현 검증에 포함하지 않았다. APK 실행량 제한·소유자별 상태·프로세스 종료 경계는 합성 테스트로 확인했다.
- 첫 배포는 schema epoch 2이며 구버전으로 이미지만 바꾸는 복귀를 허용하지 않는다. 배포 전 [오프라인 이전 절차](../../deploy/release-management.md)를 따르고 일치하는 DB·파일 백업을 준비해야 한다. 릴리스 버전 확정, 커밋·푸시·배포는 이 구현 작업에서 수행하지 않는다.
