# 번역 원문·작업 수명 검토 (2026-10-19)

운영 배포·컨테이너/운영 DB 변경·유료 API 호출 없이 저장소와 임시 PostgreSQL, 합성 본문으로 검토한다. UI 디자인/배치는 변경하지 않는다. 이 문서는 검증 결과에 따라 갱신한다.

## 공통 불변조건

1. 원문은 계정, 저장/스트리밍 구분, 작품/회차, 정규화한 문단 ID·순서·텍스트로 식별한다. 다른 회차 추가는 대상 회차의 정체성을 바꾸지 않는다. 소유권·휴지통·회차 존재는 모든 저장 결과 조회와 worker commit의 필수 조건이다.
2. 표시·비용 발생 요청은 현재 리더 세션에만 속한다. 계정/client, repository, 저장/스트리밍 전환, 회차/원문, 설정 revision이 바뀌면 이전 요청·폴링·다음 화 준비는 수명을 끝낸다. 늦게 도착한 응답은 수명을 되살리지 못한다.
3. 설정/키 변경·취소가 수락된 뒤 이전 실행은 결과나 완료 상태를 저장하지 못한다. 부분 결과와 완료 상태는 같은 검증/잠금 경계에서 저장한다. 저장된 검증 결과만 재시작에 재사용한다.
4. 수동 동작은 자동 조회/시작보다 우선한다. 숨김·원문 선택·취소 뒤 아직 접수되지 않은 자동 요청이나 다음 화 요청을 새로 보내지 않는다. 이미 제공자에 전달한 요청의 과금 취소는 보장하지 않는다.
5. 다음 화 원문과 언어는 다음 화 자체에서 얻는다. 이미지/구분자 등 비텍스트는 공통 정규화에서 제외하며 빈 텍스트는 과금하지 않는다. 긴 문단은 모든 조각 완료 전 표시하지 않는다.

worker의 마지막 output commit과 `complete` 전환을 같은 트랜잭션에 합쳤다. 이전 구현은 원문 검증 후 별도 statement로 완료 상태를 기록했다. 이 간격은 코드 검토로 확인했으며, 독립적인 실서비스 경쟁 재현으로 확정한 문제와 구분한다. 계정 잠금 후 작품 잠금을 잡는 순서를 요청과 commit에서 통일한다. 취소의 응답 실패를 성공으로 간주하지 않으며, polling catch에도 세션 epoch와 abort를 확인한다. DELETE 실패 및 DELETE 성공 후 조회 실패, abort를 무시한 늦은 poll의 회귀를 추가했다.

- 임시 PG에서 최대 500,000자/10,000문단 입력의 정확한 source proof를 10회 실행: 평균 **33.24ms**, 최대 **36.18ms**. 쿼리에는 실제 `jsonb_agg`/동등성 검사가 포함된다. 이 환경의 단일 작업 측정에서 2초 worker 확인 간격보다 충분히 짧았다. 운영 부하·동시 다중 계정·DB 장비 차이의 성능을 보장하는 수치는 아니다.
- 기존 캐시·진행 작업의 스키마나 ID를 변경하지 않는다. 새 요청은 provenance hash를 쓰지만 기존 hash의 queued/running/complete/부분 결과도 같은 `book_id`에서 재사용한다. book purge의 FK cascade 뒤 동일 ID 작품이 생겨도 이전 작업은 남지 않는다.

## 남은 경계와 미검증

- 실제 제공자별 IAM/출력 품질·유료 호출, 실기기 OS, 운영 백업 복원, Redis stall/복수 worker의 중복 실행 및 과금은 이번 합성 검증의 범위 밖이다. 실행 ID로 이전 실행의 commit을 차단하는 계약은 유지하지만 모든 외부 호출 중복을 증명하지 않았다.
- 서버에서 이미 수락한 화는 화면 숨김/종료 뒤 완료될 수 있다. 취소/키 변경 전 이미 전달한 제공자 요청의 비용을 되돌릴 수는 없다. 취소와 provider 전송 사이의 모든 네트워크 시점은 실 제공자로 검증하지 않았다.
- `chapterTextHash`는 본문 hash이므로 stale revision admission에 쓰며, 정확한 작업 원문은 서버의 현재 문단 snapshot과 `input` 동등성으로 보호한다. 동일 본문을 다른 ID로 재분할한 오래된 리더에서는 새 결과가 표시되지 않을 수 있어 재열기가 필요하다.
- 앞선 브라우저 검사에서 한 번 관측한 데스크톱 끝 이동 행 겹침은 원인 미확정이다. 이번 변경은 표시 컴포넌트/CSS/배치를 건드리지 않았고 브라우저 레이아웃 검사를 반복하지 않았다.
- 운영 배포, 컨테이너/운영 DB 변경, 커밋/푸시/릴리스는 수행하지 않았다. 사이트별 데이터/확장은 사용하지 않았다.

## 부모 에이전트의 독립 재검토 (2026-10-19)

앞선 핵심 코드 열람만으로 변경 전체를 충분히 검토했다고 볼 수 없었다. 이번에는 추가 위임 없이 위 기준본 대비 11개 파일의 변경과 현재 실행 코드를 대조하고, 저장/스트리밍 식별, SQL 원문 비교, 계정→작품 잠금 순서, 키 변경/취소, 최종 output/완료 트랜잭션, 리더 세션과 비동기 응답 수명을 확인했다. UI 컴포넌트·CSS 및 운영 환경은 변경하지 않았다.

새로 작성한 hook 테스트에서 두 누락을 재현하고 직접 수정했다. 첫 사례는 controller.start를 직접 다시 호출하는 방어 경계 검사이며, 현재 UI는 작업 진행 중 시작 버튼을 숨기므로 실제 버튼 조작만으로 같은 순서가 발생한다고 입증한 것은 아니다. 두 번째 사례는 실제 취소 흐름의 지연 조회를 재현한다.

- 이전 정기 조회가 새 수동 요청보다 늦게 끝나면 새 queued 결과를 과거 failed 결과로 덮었다. 수동 시작 시 기존 조회를 중단하고, 요청이 진행되는 동안 정기 조회를 멈춘 뒤 성공·실패 모두에서 다시 시작한다. 수정 전 실패, 수정 후 통과했다.
- 취소 직후 상태 조회가 느릴 때 정기 조회를 먼저 재개해 조회가 겹쳤다. 취소 후 조회가 끝난 다음 정기 조회를 재개한다. 이미 예약된 타이머도 네트워크 요청 전에 abort/세션을 확인하도록 했다. 수정 전 중복 조회가 재현됐고 수정 후 통과했다. 취소 요청 자체의 실패를 취소 성공으로 처리하지 않는 기존 계약은 유지한다.

추가로 수동 요청 실패 후 조회 복구, 임시 PostgreSQL에서 취소→동일 작업 재개→새 실행 완료→취소된 실행의 늦은 반환, 같은 저장 원문에 대한 HTTP 요청 8개의 동시 접수를 검사했다. 새 실행 결과는 유지됐고 동시 요청은 DB 작업 하나로 수렴했다. 이는 Redis stall/다중 worker 중복 과금 검증과는 다르다.

- 새 회귀 5개를 포함한 7개 파일 **63개 테스트 통과**. 기존 PG 통합 검사도 실제 실행했으며 skipped 없음. 로그: `/tmp/boaa-parent-review-tests-final.log`.
