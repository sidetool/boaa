# 일반 서버 TTS 묶음 크기와 낭독 누락 검토

요청: Gemini Vertex 묶음 낭독에서 표시가 빠르게 넘어가고 읽지 않은 내용이 생기는 문제. 실제 해당 유료 응답은 보관되어 있지 않아 사용자 사례의 단일 원인을 확정하지 않는다. 아래는 합성 응답으로 재현한 코드 결함과 수정이다. 운영 배포·유료 API 호출은 수행하지 않았다.

## 확인한 경계

- 화면 문단 추적은 `currentTime / duration`에 문단 글자 수 비율을 적용한 추정이다. 오디오를 잘라내거나 다음 묶음을 시작하는 타이머가 아니다. 다음 묶음은 현재 오디오의 종료를 기다린다.
- Vertex 응답 해석이 첫 오디오 part를 찾자마자 반환했다. 두 part 입력의 두 번째 PCM이 누락되는 실패를 수정 전 확인했다. 선택한 첫 candidate의 모든 음성 part를 순서대로 합친다. 다른 candidate는 대안이므로 합치지 않는다. WAV는 RIFF 헤더를 반복 연결하지 않고 PCM과 format을 검증하여 한 파일로 만든다.
- `MAX_TOKENS`, `OTHER`, `SAFETY`, `CONTINUATION` 응답에 부분 오디오가 있어도 성공 처리했다. 네 경우 모두 수정 전 테스트가 실패했다. 이제 Vertex는 `STOP` 완료만 허용하며 완료 정보 누락, 빈 오디오, 잘린 WAV와 혼합 형식을 오류로 처리한다. 일반 Gemini Interaction도 여러 오디오 part를 보존하며 명시적 미완료 status를 거절한다. 키·본문·응답 전문은 로그에 남기지 않는다.
- 재사용 Audio 요소에 이전 `ended` 이벤트가 늦게 도착했을 때 현재 음원이 끝났는지 검사하지 않았다. 현재 `ended=false`인 이벤트가 다음 음원을 완료시키는 테스트가 수정 전 실패했다. 현재 요소/실행과 종료 상태가 맞을 때만 완료한다. 실제 모바일에서 이 이벤트가 발생한 것까지 재현한 것은 아니다.
- 추정 표시 index가 오류 후 보존되는 재시작 index와 같았다. 실행 제어기에 실제 재생 묶음 시작 위치를 따로 두어 표시 이동은 재시작 위치를 바꾸지 않는다. 실패 후에는 묶음 처음부터 재시도한다. 외부 기기 세션의 실제 위치 동기화는 유지한다.
- 선언된 문단 수 안에서 문단을 못 불러온 경우 회차 완료로 처리하던 경로를 중단/오류로 바꿨다. 읽지 않은 나머지를 건너뛰고 다음 화로 진행하지 않는다.

Google의 [GenerateContent 완료 상태 계약](https://ai.google.dev/api/generate-content#FinishReason)은 STOP과 토큰 한도·기타 중단을 구별한다. [Vertex TTS 안내](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/text-to-speech/overview)와 SDK 응답 구조를 함께 확인했다. STOP도 원문을 의미적으로 빠짐없이 발화했다는 증명은 아니다. 그런 누락을 판별하려면 별도의 음성 인식/정렬이 필요하며 이번 작업에 추가하지 않았다.

## 묶음 설정

`세부 청취 설정 → 읽는 방식 → 합성 단위: 묶음 → 묶음 크기`에서 200~2000자, 기본 700자. 기존 문장/문단 기본 동작은 유지한다. 최대 16문단 제한은 유지하며 긴 한 문단도 설정한 크기에 맞춰 나눈다. Unicode code point 기준이며 줄바꿈을 포함한다.

`plainBatchCharacters`는 기존 전역/작품별 재생 설정 경로로 저장하고 정규화한다. 현재 화, 다음 화 준비, 클라이언트 요청과 서버 원문 재구성에 같은 값을 적용한다. 변경 시 현재 재생/미리 준비를 멈추고 이전 재시작 fingerprint를 무효화한다. 본문/회차/소유권 검증을 생략하지 않으며 잘못된 크기는 서버가 거절한다.

Gemini 일반 낭독 캐시 키에 음성 검증 버전을 추가해 이전 코드가 저장한 잘린 음성을 다시 사용하지 않는다. 다른 엔진의 캐시는 유지한다. 미완성 응답은 성공 캐시에 저장하지 않으며 무조건 자동 재호출하여 비용을 늘리지 않는다. 기존 429 대기 정책은 유지한다.

운영 반영, 커밋, 푸시는 하지 않았다. 사용자 사례의 실제 음성 내용과 정상 완료 응답 안의 의미적 누락은 확인하지 않았다.

## 후속: 재생 중 조절과 음성 재사용 (2026-10-20)

일반 서버 TTS의 합성 속도를 1배로 고정하고, 재생 속도는 `HTMLAudioElement.playbackRate`로 적용한다. 배속·음량 변경 시 같은 음원과 위치를 유지하며 pitch 보존을 켠다. 미리듣기도 같은 방식이다. 화자별 합성이나 기기 TTS의 합성 속도 계약은 바꾸지 않았다. 일반 서버 TTS 이어듣기 식별에서 배속은 제외하며 목소리/본문 등 합성 조건은 유지한다.

설정의 수면 타이머를 현재 세션에도 반영한다. 타이머 변경·해제로 음성 재생을 재시작하지 않는다. 기존 정책대로 준비/일시정지 시간은 제외하고, 시간이 다 되면 현재 낭독 항목(묶음)을 마친 뒤 멈춘다. 이전 세션의 늦은 종료가 새 세션의 타이머를 멈추지 않도록 했고, 재개 대기 직후에도 세션 유효성을 다시 검사한다.

읽기 세션에 메모리 음성 캐시를 둔다(최대 8개/32MiB, 저장소 영구 보관 아님). 준비 중인 같은 요청은 하나로 합치고, 재생 취소는 그 대기자만 분리한다. 이미 전송한 유료 요청의 결과는 재사용할 수 있게 유지한다. 계정/런타임/본문 소유권 교체나 unmount 시 요청 취소와 캐시 정리를 수행한다. 실패는 캐시하지 않는다. 키에는 회차·원문 해시/리비전·목소리/모델·필터·묶음 조건이 포함된다. 조건 변경 후 다른 음성을 재사용하지 않는다. 캐시 한도 초과 시 오래된 결과부터 제거하며 진행 중 요청 수도 제한한다.

이미 요청한 묶음 안의 문단을 선택하면 그 묶음 시작으로 되돌려 같은 오디오를 재생한다. 이전·다음 버튼은 알려진 묶음 경계를 사용하며, 이동 안내와 기존 세부 설정 설명에 이를 명시했다. 정확한 문단별 타임스탬프가 없으므로 추정 시각으로 오디오를 잘라내지는 않는다. 아직 준비하지 않은 구간, 다른 합성 조건, 페이지 새로고침/메모리 퇴출 뒤에는 요청이 필요할 수 있으며 서버의 기존 캐시 정책을 따른다. 모든 재요청이 유료 제공자 재호출을 뜻하는 것은 아니다.

검증: 관련 17개 파일 테스트, 웹 타입검사, 변경 파일 ESLint/Prettier. 실제 Chromium에서 합성한 테스트 WAV를 사용해 배속 변경 전후 같은 audio/src 유지, 재생 위치 유지, 일시정지 중 배속 변경과 재개를 확인했다. 실제 유료 API와 휴대폰 실기 테스트는 하지 않았고, 운영에는 반영하지 않았다. 로그 `/tmp/boaa-tts-reuse-tests-final.log`, `/tmp/boaa-tts-reuse-tsc-final.log`; 브라우저 검사 `/tmp/boaa-tts-live-audio-smoke.mjs`.
